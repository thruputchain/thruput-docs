## Overview

The Groundhog CLI ships a `codegen` subcommand that emits a self-contained TypeScript file from a contract's [spec](/reference/contract-spec/). The generated module gives you:

- TypeScript types for every struct, enum, and union declared by the contract
- A typed function per public entrypoint that builds calldata and decodes return values
- The contract's interface metadata (selectors, entrypoint IDs) as constants

The output is one file. No build step, no dependencies beyond a small runtime helper, no transitive npm packages.

## Generating Bindings

After building your contract, run:

```bash
groundhog codegen ts ./target/wasm32-unknown-unknown/release/my-contract.wasm -o ./web/src/contracts/my-contract.ts
```

The source is a built contract artifact: either the `.wasm` itself (the spec is embedded in it) or the `.spec.xdr` sidecar that `groundhog build` writes next to it. Pass `--output`/`-o` to write the result to disk, or omit it to print to stdout.

You can also generate the bindings as part of the build:

```bash
groundhog build --bindings ts
```

which writes `<artifact>.ts` next to the wasm.

`groundhog build` additionally writes a human-readable `<artifact>.spec.json` sidecar for inspecting the contract's interface; see [Contract Spec](/reference/contract-spec/) for the full format.

See `groundhog codegen ts --help` for the full set of flags.

## What the Output Looks Like

For a counter contract with one method, the generated file contains:

```typescript
import { ContractAddress } from "<helper-import>";

// Type definitions from the contract spec
// (Each struct, enum, and union annotated with #[contract_type]
// or used in a method signature shows up here.)

// Interface and entrypoint metadata
export const COUNTER_SPEC = {
  // selectors, entrypoint IDs, version, etc.
} as const;

// One function per method
export async function increment(
  client: GroundhogClient,
  contract: ContractAddress,
  amount: bigint,
): Promise<bigint> {
  // builds the call, signs/sends via the JSON-RPC gateway,
  // and decodes the response.
}
```

(The exact runtime helper imports depend on the gateway client library you bind against. The generated file is intentionally framework-agnostic.)

## Type Mapping

The codegen maps Rust contract types to TypeScript as follows:

| Rust contract type | TypeScript type |
|--------------------|-----------------|
| `bool` | `boolean` |
| `u32`, `i32`, `u64`, `i64`, `u128`, `i128` | `bigint` |
| `String` | `string` |
| `Bytes`, `Vec<u8>`, `[u8; N]` | `Uint8Array` |
| `ContractAddress` | `ContractAddress` (32-byte tagged type) |
| `Option<T>` | `T \| null` |
| `Vec<T>` (non-`u8`) | `T[]` |
| `(A, B, ...)` | `[A, B, ...]` |
| Named struct | TypeScript interface |
| Named enum | Discriminated union (tag + payload) |
| Named union | Discriminated union |

`u8` is intentionally rejected as a bare type: it must appear inside a `Vec` or `Array` so the generated TypeScript can use `Uint8Array`. See `groundhog-rpc/crates/tools/cli/src/codegen.rs` for the full mapping.

## When You'd Use This

- A web frontend that calls a contract you control. Run `groundhog codegen ts` after every contract change and check the output into your frontend repo.
- A Node.js script that signs and submits transactions. The generated functions handle calldata encoding; you provide the signer and the gateway URL.
- An indexer or backend service that wants typed event decoding.

For pure read access without a typed client, see the [JSON-RPC API](/reference/json-rpc-api/) reference: every method shown there can be called with any JSON-RPC 2.0 library.

## What's Coming

A higher-level developer package (transaction building, wallet integration, contract-aware caching, event subscriptions) is planned. Until it lands, the supported path is per-contract codegen plus direct JSON-RPC calls. The JSON-RPC gateway is the only supported wallet/transaction-submission entry point.
