We're building the counter contract generated by `groundhog new`. It has initialize, increment, decrement, and get operations, plus a small event example and an explicit error example. The counter demonstrates the core idea: use `strict_inc` to record a change instead of replacing the counter with a newly calculated value. Concurrent changes can then combine.

**Prerequisites:** Complete the [Getting Started](/start/getting-started/) guide for SDK setup.

:::note[Version checked]
This tutorial follows the latest tagged CLI template, `0.10.2`, which uses SDK `0.21.0` and `groundhog-json-rpc-client` `0.9.6`. Current CLI `0.10.3` source has moved its template to SDK `0.23.1` and RPC client `0.10.2`, but that CLI release is not available yet.
:::

## What You'll Build

A contract with four core counter methods and two scaffold examples:

| Method | Signature | What it does |
|--------|-----------|-------------|
| `initialize` | `(&mut self, initial_value: u64)` | Add the initial amount. Call it once after deployment by convention. |
| `increment` | `(&mut self, amount: u64)` | Add to the counter |
| `decrement` | `(&mut self, amount: u64)` | Subtract from the counter (aborts if result would be negative) |
| `get` | `(&self) -> u64` | Read current value |
| `ping` | `(&self, tag: u64)` | Emit a simple event |
| `error` | `(&self) -> u64` | Throw the declared contract error |

## Step 1: Project Setup

Create a new contract crate:

```bash
groundhog new counter
cd counter
```

The generated `Cargo.toml` includes both the library contract and the RV32 (32-bit RISC-V) entrypoint wrapper:

```toml
[package]
name = "counter"
version = "0.1.0"
edition = "2024"

[lib]
crate-type = ["cdylib", "rlib"]
doctest = false
test = false

[[bin]]
name = "counter"
path = "src/main.rs"
required-features = ["rv32-entrypoints"]
test = false
bench = false

[features]
entrypoints = []
rv32-entrypoints = ["entrypoints"]
default = ["dev"]
dev = ["sdk/dev"]
groundhog-integration-test = ["dep:groundhog-json-rpc-client", "dep:tokio"]

[dependencies]
sdk = { version = "0.21.0", registry = "groundhog" }

[target.'cfg(not(target_arch = "riscv32"))'.dependencies]
groundhog-json-rpc-client = { version = "0.9.6", registry = "groundhog", optional = true }
tokio = { version = "1", features = ["macros", "rt-multi-thread"], optional = true }

[dev-dependencies]
counter = { path = ".", features = ["dev"] }
```

Your `src/lib.rs`:

```rust
#![cfg_attr(not(feature = "dev"), no_std)]

sdk::declare_mock_contract!();

mod implementation;

pub use implementation::Counter;
pub use implementation::CounterClient;
```

The crate is `no_std` whenever the `dev` feature is disabled. Native development builds enable `dev` by default; `groundhog build` disables default features for contract artifacts.

## Step 2: Define the Error Type

Contracts need a contract exception type only when they declare domain exceptions through `throws`. The generated counter includes one as an example. `#[contract_exception]` generates serialization and XDR encoding, and each variant maps to an integer discriminant.

```rust
use sdk::storage::NNInt;
use sdk::*;

#[contract_exception]
pub enum CounterError {
    NotAuthorized = 1,
}
```

This counter doesn't use authorization, so `NotAuthorized` is a placeholder exercised by the scaffold's `error` method. A contract without domain exceptions can omit `throws` and the exception type. Storage failures, such as a counter going below zero, remain SDK library exceptions.

The scaffold also includes a tiny event type:

```rust
#[derive(Event, Clone, Debug)]
pub struct PingEvent {
    #[topic]
    pub tag: u64,
}
```

`#[topic]` marks the field as an indexed event topic. The full event flow is covered in [Add Events to a Contract](/tutorials/add-events-to-a-contract/).

## Step 3: Define Storage

```rust
#[derive(Debug)]
#[sdk::storage]
pub struct Counter {
    value: NNInt,
}
```

The `#[sdk::storage]` macro generates serialization and persistence code. Each field becomes a storage slot. [`NNInt`](/programming-model/storage-types/#nnint) is Groundhog's integer storage type for signed changes. Those [deltas can merge](/programming-model/execution/#merged-deltas) across concurrent transactions.

One field is all this contract needs. More complex contracts use `Map<K, V>` for key-value storage (see [Build a Token](/tutorials/build-a-token/)).

## Step 4: Implement the Contract

```rust
#[contract(throws = CounterError, emits(PingEvent))]
impl Counter {
    pub fn initialize(&mut self, initial_value: u64) {
        self.value.strict_inc(initial_value as i128);
    }

    pub fn increment(&mut self, amount: u64) {
        self.value.strict_inc(amount as i128);
    }

    pub fn decrement(&mut self, amount: u64) {
        self.value.strict_inc(-(amount as i128));
    }

    pub fn get(&self) -> u64 {
        self.value.try_get().unwrap_or(0) as u64
    }

    pub fn ping(&self, tag: u64) {
        log_event(&PingEvent { tag });
    }

    pub fn error(&self) -> u64 {
        throw(CounterError::NotAuthorized);
    }
}
```

Line by line:

- **`#[contract(throws = CounterError, emits(PingEvent))]`** generates contract entrypoints, a `CounterClient` struct for cross-contract calls and testing, and spec metadata for the declared error and event. The client name defaults to `{StructName}Client`. You can override it with `client = CustomName` if needed.

- **`strict_inc(delta)`** records a signed change. `increment(5)` records `+5`, while `decrement(5)` records `-5`. Concurrent calls can combine those changes instead of competing to replace the counter with different final values. `strict_inc` takes `i128`, so the scaffold casts the `u64` amount and negates it for decrements.

- **`strict_inc` aborts on underflow.** If the counter is at 3 and you call `decrement(5)`, the result would be -2. `NNInt` rejects the change and the transaction aborts automatically. You don't need to check for this.

- **`try_get().unwrap_or(0)`** reads the current value. `try_get()` returns `Result<i128, LibraryExn>`; the scaffold's `unwrap_or(0)` therefore maps every read error to zero, not only missing storage. Production code that should default only missing storage uses `try_get().none_if_missing().unwrap_or(0)`.

- **`as u64` narrows the stored value.** `NNInt` stores `i128`, so a value above `u64::MAX` would truncate in this scaffold. A production counter should return `i128` or perform a checked conversion with a domain error.

- **`initialize` is not automatic or guarded.** Deployment and initialization are separate calls. Calling `initialize(10)` twice adds 20 because the scaffold does not store an initialized flag.

- **`&self` vs `&mut self`**: `get` takes `&self` (read-only), so it reads from the snapshot without recording a storage change. The other methods take `&mut self` and update state.

- **`ping` and `error`**: these are scaffold examples for events and explicit exceptions. They are not part of the counter logic, but they give you working code to modify.

## Step 5: Test It

The scaffold creates `tests/test.rs`:

```rust
use counter::{register_mock_contract, CounterClient};
use sdk::*;

static NONCE: SHA256Hash = sdk::sha256_static!("COUNTER_NONCE");

fn setup() -> (TestEnvironmentHandle, SHA256Hash) {
    let env = TestEnvironment::no_cost();
    let test_contract = register_mock_contract(&env);
    let contract_hash = test_contract.as_hash().clone();
    (env, contract_hash)
}

#[test]
fn test_counter() {
    let (env, contract_hash) = setup();

    env.transact(|tx| {
        let caller = <ContractAddress as Named>::named("test_counter");
        tx.call(&caller).run(move || {
            let addr = deploy_contract(&NONCE, &contract_hash);
            let client = CounterClient::new(&addr);

            client.initialize(10);
            assert_eq!(client.get(), 10);

            client.increment(5);
            assert_eq!(client.get(), 15);

            client.decrement(3);
            assert_eq!(client.get(), 12);
        })
    })
    .assert_success();
}
```

Breaking down the test setup:

1. **[`TestEnvironment::no_cost()`](https://groundhog.dev/docs/sdk/latest/sdk/struct.TestEnvironment.html#method.no_cost)** creates an in-process test environment with storage costs disabled. Good for logic tests.
2. **`register_mock_contract(&env)`** registers the contract with the test environment. This function is generated by `declare_mock_contract!()` in your `lib.rs` and available when the `dev` feature is enabled.
3. **`test_contract.as_hash().clone()`** gets the contract hash for deployment.
4. **`env.transact(...)`** runs the closure as a single auto-committed transaction. `tx.call(&caller)` sets the address the transaction originates from; `.assert_success()` panics with details if the transaction did not commit. The returned `TransactResult` also records emitted events. See [Add Events to a Contract](/tutorials/add-events-to-a-contract/).
5. **`deploy_contract`** deploys the contract and returns its address. The nonce (`SHA256Hash`) makes the address deterministic across test runs.
6. **`CounterClient::new`** creates a typed client. Methods return values directly (no `Result` unwrapping needed).

Use [`TestEnvironment::default()`](https://groundhog.dev/docs/sdk/latest/sdk/struct.TestEnvironment.html#method.default) instead when the test should exercise the normal storage cost model. Use `TestEnvironment::new(Some(&model))` for custom cost-model tests. For the generated SDK reference, see [Rust API Docs](/tools/rust-api-docs/).

### Testing Error Cases

Use `try_*` methods to verify that operations fail as expected:

```rust
#[test]
fn test_counter_underflow() {
    let (env, contract_hash) = setup();

    env.transact(|tx| {
        let caller = <ContractAddress as Named>::named("test_counter_underflow");
        tx.call(&caller).run(move || {
            let addr = deploy_contract(&NONCE, &contract_hash);
            let client = CounterClient::new(&addr);

            client.initialize(5);

            // Decrementing by 10 should abort: strict_inc rejects a negative result
            assert_eq!(
                client.try_decrement(10).unwrap_err().try_as(),
                Some(LibraryExn::NonNegativeIntUnderflow),
            );
        })
    })
    .assert_success();
}
```

The `try_decrement` method (generated by the `#[contract]` macro alongside `decrement`) returns a `Result` instead of aborting. The error type is the SDK's `CallError`; `try_as` decodes the caught exception as whichever exception type you name — here the SDK's own `LibraryExn`, which is matched exactly like a contract's error type.

### Native Logic vs RV32 Integration

Run the fast native tests first:

```bash
cargo test
```

Then build the deployable RV32 artifact:

```bash
groundhog build
```

The scaffold includes `tests/integration.rs`. Run it against an ephemeral local node:

```bash
groundhog test --integration
```

That command deploys RV32 with the runtime's lowest-index `local_user`, normally `dev-1`, and sets `GROUNDHOG_INTEGRATION_TEST=1` to activate the scaffolded test. It also provides `GROUNDHOG_RPC_URL`, `GROUNDHOG_CONTRACT_ADDRESS`, `GROUNDHOG_PROFILE`, `GROUNDHOG_DEFAULT_KEY`, and `GROUNDHOG_RUNTIME_MANIFEST` to the integration test process. Plain `groundhog test` runs the generated executor-backed RV32 test.

## Why This Matters

This counter is small, but the pattern scales. If 1,000 admitted transactions increment the same counter by 1, their changes can combine to `+1000`. Block capacity and scheduling still determine how many transactions are admitted, and decrements still cannot take an ordinary counter below zero.
