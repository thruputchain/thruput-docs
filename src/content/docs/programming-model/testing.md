## Test Modes

Start with `cargo test` for native logic tests in process, then run `thruput test` against the RV32 artifact. Add `thruput test --integration` when you need to test the same path a partner or app will use: build artifact, local node, deployment, signing profile, RPC URL, and generated client behavior. [Build and test](/cli/build-and-test/#choose-a-test-boundary) compares the three modes and their command options.

Fresh projects include the integration target and host-only dependencies. The CLI can acquire a compatible catalog-pinned `hog-devnode`; use `thruput toolchain list` to inspect it. `THRUPUT_DEVNODE_BINARY` selects an explicit matching source build.

## What the Scaffold Gives You

Every new project (the default minimal contract, `--template counter`, and `--template counter-app`) includes:

```text
build.rs
tests/
  test.rs
  test_rv32.rs
  integration.rs
```

`tests/test.rs` holds native tests, and `tests/test_rv32.rs` runs under `thruput test`.

`tests/integration.rs` starts with one ignored RPC smoke test. It checks that the CLI provided a base58 contract address, connects to the ephemeral node with `thruput-json-rpc-client`, and calls `getChainTip`. Replace or extend the final placeholder with assertions for your contract.

The starter remains ignored under ordinary `cargo test`, even if you explicitly enable its feature. `thruput test --integration` enables the feature and sets `THRUPUT_INTEGRATION_TEST=1`, which lets the scaffold's `build.rs` activate the live test. You can rename the module and test functions without changing how activation works.

The generated `thruput-integration-test` feature enables the optional RPC client and Tokio dependencies. Their target-specific Cargo entries keep them out of RV32 guest builds. Preserve the SDK and RPC versions selected together by the scaffold.

The generated `build.rs` contains:

```rust
fn main() {
    println!("cargo:rerun-if-env-changed=THRUPUT_INTEGRATION_TEST");
    println!("cargo:rustc-check-cfg=cfg(thruput_integration_runner)");

    if std::env::var("THRUPUT_INTEGRATION_TEST").as_deref() == Ok("1") {
        println!("cargo:rustc-cfg=thruput_integration_runner");
    }
}
```

:::tip[Projects created with an older scaffold]
Compare with a fresh scaffold, then add `tests/integration.rs`, its feature and host-only dependencies, and the integration activation logic from `build.rs`. If your project already has a build script, merge the activation lines into its existing `main` function. The CLI exits with `integration_test_not_found` when the test target is absent.
:::

## Test Setup

Your `lib.rs` must include `thruput_sdk::declare_mock_contract!()` to generate the `register_mock_contract` function used in tests:

```rust
#![cfg_attr(not(feature = "dev"), no_std)]

thruput_sdk::declare_mock_contract!();

mod implementation;
pub use implementation::*;
```

## Basic Pattern

```rust
use thruput_sdk::*;

use my_counter::{CounterClient, register_mock_contract};

static NONCE: SHA256Hash = thruput_sdk::sha256_static!("COUNTER_NONCE");

fn setup() -> (TestEnvironmentHandle, SHA256Hash) {
    let env = TestEnvironment::no_cost();
    let test_contract = register_mock_contract(&env);
    let contract_hash = *test_contract.as_hash();
    (env, contract_hash)
}

#[test]
fn test_counter() {
    let (env, contract_hash) = setup();

    env.transact(|tx| {
        let caller = ContractAddress::named("test_counter");
        tx.call(&caller).run(move || {
            let addr = deploy_contract(&NONCE, &contract_hash);
            let client = CounterClient::new(&addr);

            client.initialize(10);
            client.increment(5);
            assert_eq!(client.get(), 15);
        })
    })
    .assert_success();
}
```

Breaking this down:

1. **[`TestEnvironment::no_cost()`](https://docs.rs/thruput-sdk/latest/thruput_sdk/struct.TestEnvironment.html#method.no_cost)** creates an in-process test environment with storage costs disabled.
2. **`register_mock_contract(&env)`** registers the contract with the test environment. This function is generated by `declare_mock_contract!()`.
3. **`*test_contract.as_hash()`** copies the contract hash for deployment.
4. **`env.transact(...)`** runs the closure as a single auto-committed transaction. `tx.call(&caller)` sets the address the transaction originates from, and `.run(closure)` executes the closure in a simulated execution context. The returned `TransactResult` records the outcome, return value, and emitted events. `.assert_success()` panics with details if the transaction did not commit.
5. **`deploy_contract`** deploys the contract and returns its address. The nonce makes the address deterministic.
6. **`CounterClient::new`** creates a typed client. Methods return values directly.

## `no_cost` vs `default`

Use [`TestEnvironment::no_cost()`](https://docs.rs/thruput-sdk/latest/thruput_sdk/struct.TestEnvironment.html#method.no_cost) for most contract logic tests. It disables storage cost enforcement, which keeps tests focused on method behavior, storage mutations, events, and expected exceptions.

Use [`TestEnvironment::default()`](https://docs.rs/thruput-sdk/latest/thruput_sdk/struct.TestEnvironment.html#method.default) when the test should exercise the normal storage cost model. This is useful for storage-token behavior, deployment cost checks, or tests that should fail when the caller has not been funded correctly.

Use `TestEnvironment::new(Some(&model))` when the test is specifically about a custom `StorageCostModel`. Use `setup_grant_storage_tokens` to fund accounts in cost-sensitive tests.

For the full generated API, see the [`TestEnvironment` Rustdoc](https://docs.rs/thruput-sdk/latest/thruput_sdk/struct.TestEnvironment.html) or [Rust API Docs](/tools/rust-api-docs/).

When a native test needs a custom transaction context, start with `env.transaction()`. The builder currently supports replacing the default authorization claim:

```rust
let result = env
    .transaction()
    .with_auth_claim(auth_claim)
    .transact(|tx| tx.call(&caller).run(|| {
        // contract calls
    }));
```

Finish the builder with `transact` for auto-commit, `transact_manual` for explicit commit or abort control, or `build` to obtain a `MockTransactionHandler` directly. Plain `env.transact(...)` remains the shorthand for the default transaction configuration.

Use `thruput test --integration` when the thing under test is not just contract logic: local node startup, RV32 artifact deployment, profile resolution, signing, RPC environment variables, or generated off-chain client behavior.

## Testing Error Cases

Use `try_*` methods to verify that operations fail as expected:

```rust
// Inside tx.call(&caller).run(...), after client.initialize(5):
assert_eq!(
    client.try_decrement(10).unwrap_err().try_as(),
    Some(LibraryExn::NonNegativeIntUnderflow),
);
```

The `try_decrement` method (generated alongside `decrement` by the `#[contract]` macro) returns a `Result` instead of aborting. The error type is the SDK's `CallError`, which is the same for every client: a caught exception stays undecoded inside it, and `try_as` decodes it as whichever exception type you name. When more than one type is of interest, `match_exn!` matches several in one place. See [Handle errors](/contracts/errors/) for the full error model.

## Blocks and Conflicts

Each `env.transact` call runs in the current block. Transactions in the same block read the previous block's committed state and do not see each other's writes. Call `env.advance_block()` to commit the block and make its effects visible. Use `env.advance_block_at(timepoint)` to pin the next block's time for deadline and expiry tests.

Use same-block transactions to test merges and exclusion:

```rust
fn transfer(env: &TestEnvironmentHandle, from: ContractAddress, to: ContractAddress, amount: i128) -> TransactResult {
    env.transact(|tx| tx.call(&from).run(move || ERC20Client::new(&token()).transfer(&to, amount)))
}

// Alice holds 100. Both transfers run in the same block.
transfer(&env, alice(), bob(), 60).assert_success();
transfer(&env, alice(), carol(), 60).assert_commit_failed_nondeterministically();
env.advance_block();
```

`assert_commit_failed_nondeterministically()` means the root call succeeded but its deltas could not be reserved with the block's other changes. On a network, that attempt is excluded from the proposal. This assertion does not test scheduler requeue, RPC status, or client resubmission. See [Exclusion, requeue, and resubmission](/how-it-works/transaction-lifecycle/#exclusion-requeue-and-resubmission) for those separate behaviors.

`TransactResult` also provides `assert_return_as::<T>()`, `assert_abort_as::<E>()`, `events()`, and `filter_events::<E>()`. See [`contracts/erc20/tests/same_block.rs`](https://github.com/thruputchain/thruput-examples/blob/main/contracts/erc20/tests/same_block.rs) for more same-block cases.

## Integration Test Environment

`thruput test --integration` runs `tests/integration.rs` against an ephemeral `hog-devnode`. The CLI builds and deploys the selected artifact, then sets:

| Variable | Value |
|----------|-------|
| `THRUPUT_INTEGRATION_TEST` | `1`; activates the scaffolded live test |
| `THRUPUT_RPC_URL` | RPC URL for the ephemeral node |
| `THRUPUT_CONTRACT_ADDRESS` | Deployed contract address |
| `THRUPUT_PROFILE` | `integration` |
| `THRUPUT_DEFAULT_KEY` | `integration`, a temporary key the CLI creates and funds for this run |
| `THRUPUT_RUNTIME_MANIFEST` | Runtime manifest path, when available |
| `XDG_CONFIG_HOME` | Temporary config directory that holds the `integration` key and profile |

The full run is:

1. Build the RV32 artifact.
2. Start an isolated local node.
3. Deploy it with a temporary `integration` key that the CLI generates and funds at node genesis.
4. Enable `thruput-integration-test` and run only the `integration` Cargo test target with the environment above.
5. Shut down the node after the test run, including after test failures.

Normal test-harness controls such as `--match-test`, `--skip`, `--fail-fast`, `--show-output`, `--no-capture`, and `--test-threads` apply to integration tests. `--watch`, `--rerun`, and `--workspace` cannot be combined with `--integration` yet.

Integration tests use the same RV32 artifact path as normal builds and deployments.

## Testkit

`thruput-testkit` tests an application the way it is used: as several users acting at once. A `Scenario` runs a group of agents as ordinary async Rust, each with its own deterministic account. Agents deploy contracts, call them through typed proxies, coordinate over a mailbox, and assert on what they observe.

Add testkit and Tokio as dev-dependencies:

```bash
cargo add --dev thruput-testkit
cargo add --dev tokio --features macros,rt-multi-thread
```

Typed proxies come from `thruput-sdk`'s `remote` feature. To enable it for tests, add a `remote` feature to the contract crate and turn it on in the scaffold's dev-dependency on the crate itself:

```toml
[features]
remote = ["thruput-sdk/remote"]

[dev-dependencies]
my-counter = { path = ".", features = ["dev", "remote"] }
```

With the feature on, `#[contract]` generates a `CounterRemote` proxy for the `Counter` contract. Each proxy method encodes its arguments and returns a prepared invocation. Awaiting a method declared `pure` or `readOnly` simulates it. Awaiting any other method, including one without an effect annotation, submits it through the agent's wallet. Either way, the result is the decoded return value.

This scenario launches a local node, deploys Counter from one agent, and sends its address to a second agent that increments it:

```rust
use my_counter::CounterRemote;
use thruput_testkit::xdr::types::ContractAddress;
use thruput_testkit::{Agent, DeployOptions, LocalNetworkConfig, NetworkConfig, Scenario};

#[tokio::test]
#[ignore = "needs built counter contract"]
async fn two_agents_share_a_counter() -> thruput_testkit::Result<()> {
    let scenario = Scenario::builder("counter-test")
        .network(NetworkConfig::local(LocalNetworkConfig::default()))
        .artifact("counter", "../../target/thruput/my_counter.rv32a")
        .build()
        .await?;

    let deployer = Agent::new("deployer", |mut ctx| async move {
        let deployed = ctx
            .deploy_artifact("counter", DeployOptions::funded(100_000_000))
            .await?;
        ctx.send("user", &deployed.address)?;
        Ok(())
    });

    let user = Agent::new("user", |mut ctx| async move {
        let address = ctx
            .recv_from::<ContractAddress>("deployer")
            .await
            .expect("deployer sends an address")?
            .body;
        let counter = CounterRemote::new(ctx.caller().clone(), &address);
        counter.increment(5).await?; // submitted
        assert_eq!(counter.get().simulate().await?, 5); // if `get` isn't annotated
        assert_eq!(counter.get().await?, 5); // if `get` is "readOnly"
        Ok(())
    });

    scenario.run_agents([deployer, user]).await?;
    scenario.stop().await
}
```

Declaring `get` with `#[contract(effect = "readOnly")]` means `counter.get().await?` will request simulation instead of submitting a transaction; to simulate an unannotated method, use `simulate` as above.

`run_agents` returns an error when any agent fails. `deploy_artifact` funds, deploys, and optionally initializes the contract in one transaction; `DeployOptions` sets the funding and the initializer. 

When specifying artifact (guest binary) paths, note that cargo tests run in the root directory of their surrounding crate. When running the test, ensure the artifacts have already been built (with `thruput build -p <CONTRACT>`) and provide the path to the development node by setting `THRUPUT_DEVNODE_BINARY="$(thruput toolchain which)"`.

Other features:

- **Networks.** `NetworkConfig::local` launches and owns an ephemeral node, and gives each scenario account a genesis allocation (`LocalNetworkConfig::initial_account_tokens`). `NetworkConfig::existing(rpc_url, runtime_manifest)` attaches to a running node, where accounts start empty until an agent calls `ctx.fund(amount)`. `NetworkConfig::offline(accounts)` runs agents without a chain, for coordination and timing logic. Before signing anything, the scenario checks that the endpoint serves the network named in the runtime manifest.
- **Receipts and errors.** `.with_receipt()` returns the value with its receipt, and `.receipt()` returns only the receipt, for events and gas. A reverted call is `Err(TestkitError::Reverted { .. })`.
- **Manual blocks.** Set `LocalNetworkConfig::block_driver` to `BlockDriverConfig::manual()` to put several transactions in one block:

  ```rust
  let first = counter.increment(1).submit().await?;
  let second = counter.increment(1).submit().await?;
  first.await_pending().await?;
  second.await_pending().await?;
  ctx.network().produce_block().await?;
  first.await_receipt().await?;
  second.await_receipt().await?;
  ```

- **Uncertain submissions.** Testkit never resends a transaction. When a submission's outcome is uncertain, the error keeps the original transaction hash and signed bytes for reconciliation.
- **Coordination.** Agents exchange XDR-encoded messages with `ctx.send` and `ctx.recv_from`, share a virtual clock (`ctx.clock()`), and draw from a deterministic per-agent random number generator (`ctx.rng()`).
- **Calls by name.** Without an interface crate, `Contract::new(address, "Counter", "0.1.0")` calls methods by name.

For the full API and more examples, build the testkit Rustdoc from a project that depends on it:

```bash
cargo doc -p thruput-testkit --no-deps --open
```

## Named Addresses

`ContractAddress::named("alice")` produces a deterministic address from a string. Same name always returns the same address. The method hashes the name with SHA-256 at runtime, so it cannot initialize a `static` or `const`. Bind it inside the test or a `LazyLock` instead:

```rust
#[test]
fn transfer_between_known_addresses() {
    let alice = ContractAddress::named("alice");
    let bob   = ContractAddress::named("bob");
    // ...
}
```

The `Named` trait that provides this method is re-exported through `thruput_sdk::*` when the `dev` feature is enabled.
